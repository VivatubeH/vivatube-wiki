## 0. 실행 결론과 범위

- **1차 공략:** 신입/경력무관 정규직 서버 엔지니어, Linux/Windows 시스템 운영·구축, x86 서버·스토리지 기술지원, 온프레미스 인프라 운영, 실제 구축/운영 업무를 맡는 MSP 인프라 직군. '클라우드'라는 제목만으로 DevOps 전문 기술을 요구하는 공고는 이번 30일의 1차 목표가 아니다.

## 1. 실습 아키텍처 — 독립적으로 선택한 최소 구현안

세 대 구성은 이번 30일의 채용 관련 역량(서버 운영·인증·네트워크·장애 진단)을 **한 대의 32GB 호스트에서 증명하기 위한 선택안**이다. 이는 실제 호스트 자원 확인 전 확정된 최적 구성이라는 뜻이 아니다. Linux만으로 진행하면 Windows 도메인 실무 역량이 빠지고, 장비를 더 늘리면 구축 시간·고장 가능성이 높아진다.

```text
                       집 공유기 / 인터넷 (192.168.0.0/24)
                                      |
                            Windows 11 Pro HOST
                               RAM 32GB / Hyper-V
                                      |
                     (선택) WinNAT: 외부로 나가는 연결만
                                      |
                Internal vSwitch 'LAB-INT' / 10.77.10.0/24
                                      |
              +-----------------------+---------------------+
              |                       |                     |
      DC01 Windows Server      WEB01 Rocky Linux     CL01 Windows 11 Ent
      10.77.10.10             10.77.10.20            DHCP .100~.149
      AD DS/DNS/DHCP          SSH/Nginx/logs         Domain Join/GPO/SMB
              +-----------------------+---------------------+
                                      |
                         HOST vEthernet 10.77.10.1
```

| VM/자원 | 초기 권장안 | 조건·근거 |
|---|---|---|
| DC01 | Windows Server **2025 Evaluation**(Desktop Experience), vCPU 2, RAM 4GB, 동적 VHDX 70GB, Gen2 | AD/DNS/DHCP/SMB 중심. Server 2022 정식 평가 ISO를 합법적으로 구할 수 있으면 2022로 대체 가능. |
| WEB01 | Rocky Linux 9.x, vCPU 2, RAM 2~3GB, 동적 VHDX 40GB, Gen2 | GUI 없는 서버, SSH/웹 서비스. |
| CL01 | Windows 11 Enterprise **90일 평가판**, vCPU 2, RAM 4GB, 동적 VHDX 65GB, Gen2·가상 TPM 등 요구사항 확인 | Windows 11 Home은 전통적 AD Domain Join이 불가능하므로 노트북 OS를 그대로 쓰지 않는다. |
| HOST | 32GB RAM / 기존 Win11 Pro | VM의 동시 시작 메모리 약 10~11GB + 기타 부하 여유. **디스크 실제 가용량이 미확인**이므로 Day 1에 필수 확인. |
| 가상 네트워크 | `LAB-INT` Internal, `10.77.10.0/24`, HOST `.1`, DC `.10`, WEB `.20`, CL DHCP `.100-.149` | 집 LAN `192.168.0.0/24`와 중복 금지. VM의 DHCP 브로드캐스트를 물리 LAN에 흘리지 않는다. |

**평가판 근거:** [Windows Server 2025 Evaluation은 180일](https://www.microsoft.com/ko-kr/evalcenter/evaluate-windows-server-2025), [Windows 11 Enterprise Evaluation은 90일](https://www.microsoft.com/ko-kr/evalcenter/evaluate-windows-11-enterprise). 평가판 다운로드 조건·활성화·라이선스를 확인한다. Server 평가판은 초기 10일 이내 인터넷 활성화 관련 주의가 있으므로 설치 직후 NAT 인터넷 접근 검증을 포함한다. **기존 사용 PC를 평가판으로 덮어 설치하지 말고 VM에만 설치**한다.

**인터넷 연결 의존성:** Day 5에서 기존 WinNAT 객체 충돌을 확인한 후 Day 6에 WEB01의 **실제 패키지 설치 경로**를 확인한다. Day 9의 Nginx 설치에는 저장소 또는 준비된 오프라인 패키지가 필요하다. Windows Server 평가판의 설치·활성화 요건은 실제 평가판 안내에 따라 별도로 확인하며, NAT 성공 자체를 Windows Server 설치의 절대 선행조건으로 취급하지 않는다. 충돌 때문에 WinNAT을 구성할 수 없다면 Day 5~6에 대체 경로를 먼저 결정한다. 임시 `Default Switch` 또는 External 연결은 **도메인 컨트롤러나 DHCP 서버가 될 VM에서는 가급적 사용하지 않는다**. 꼭 필요한 다운로드는 호스트에서 수행하거나, AD/DHCP 역할이 없는 WEB01의 임시 인터넷 연결로 제한한다. DC01은 처음부터 LAB-INT 전용 NIC로 설치하고, 서버 평가판의 활성화 문제는 공식 조건을 확인하여 별도 대응한다. 임시 연결도 호스트 구성을 먼저 확인하고 한 번에 하나씩 적용한다. 인터넷 경로가 없으면 패키지 설치·평가판 활성화가 막힐 수 있으므로 그 상태에서 Day 9/10을 완료 처리하지 않는다.

**가상 네트워크 안전 수칙**
1. 먼저 `Get-VMSwitch`, `Get-NetNat`, `ipconfig /all`로 기존 구성을 조사한다. 기존 NAT/WSL/Docker/VPN 구성과 충돌하면 **절대 일괄 삭제하지 않는다.**
2. 초기에는 **Internal vSwitch만 구성**하여 격리를 확인한다. 외부 통신이 필요할 때 Windows [Hyper-V NAT 공식 가이드](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/setup-nat-network)를 근거로 WinNAT을 추가한다. WinNAT 자체는 DHCP가 아니다.
3. NAT을 구성했을 때만 HOST `.1`을 게이트웨이로 사용한다. **NAT 미구성 단계에서는 잘못된 기본 게이트웨이를 억지로 입력하지 않는다.** Windows DNS 서버는 실습 내부 조회를 담당하고, 외부 DNS 질의가 필요하면 적절한 전달자를 설정한다.
4. DHCP는 `LAB-INT` 내부에만 제공한다. 물리 공유기·호스트 LAN에 외부형 vSwitch로 DHCP를 직접 연결하지 않는다. 포트 포워딩·공인 인터넷 노출 금지.
5. 변경 전 현재 IP·vSwitch·NAT 설정을 텍스트로 저장. 실습용 VM에만 장애 주입; 호스트·실사용 공유기·노트북에는 고장 실험 금지. `Checkpoint`는 유용하지만 **백업의 대체물이 아니다**.
6. SSD 실제 여유 공간 기준: OS 3대 최대 가상디스크 **할당 용량**이 175GB이고 VHDX는 동적 확장, ISO·업데이트·체크포인트·내보내기 공간이 별도로 필요하다. **실측 여유 공간이 충분하지 않으면 VM 저장 위치/백업 매체/동시 운용 방식을 먼저 조정**한다. 총 디스크 500GB라는 사실만으로 설치 가능 판정하지 않는다.

**성공 기준:** VM 3대를 필요할 때 안정적으로 구동; CL01에 자동 IP·DNS 할당, 도메인 계정 로그인/GPO 확인, WEB01 HTTP 서비스 접근, 권한별 SMB 접근 차이, 로그·모니터링·백업 복구 증명. 장애 실습 후 반드시 정상 상태로 반환.

## 2. 180시간 운영 원칙과 일정 게이트

- 하루 6시간은 **총량**이며 독서·문서·지원 모두 포함한다. 점심·휴식 제외. 강의 완주 시간 따로 추가하지 않는다.
- **Day 1~30:** 일자별 `시간 배분`을 기준으로 운영한다. 일부 날짜는 이력서·지원 시간을 늘리고 기술 실습을 줄이므로 단계별 동일 시간표를 적용하지 않는다.
- **공통 제약:** 매일 개념+실습+증거+취업+버퍼 = 360분. 30일 합계 10,800분(180시간).
- **취업 활동:** 적합 공고가 있으면 이력서 v0 상태에서도 Day 1부터 지원 가능. Day 3~5는 지원용 이력서 품질을 올리는 집중 기간.
- **지연 대응:** Day 10·17·21·27의 보충 슬롯은 해당 날짜의 실습 시간에 이미 포함되며 추가 시간이 아니다.
- 실습이 예상보다 일찍 끝나면 자격증 영상 대신 **원인 설명 → 깨뜨리기 → 복구 → 증거 저장**에 시간을 쓴다. 버퍼 30분은 낭비 시간이 아니라 예상치 못한 설치·환경 오류 대응이다.
- **Day 7/14/21/28**에 20~30분 주간 게이트: 중단·축소·보완 여부를 판정한다. 미달 시 2순위 학습부터 줄이고, 진척률을 조작하지 않는다.
- **지원 활동:** Day 1부터 공고 조사, Day 3 기본 이력서, Day 1부터 현재 이력서로 지원 가능한 적합 공고는 즉시 지원(프로젝트 미완성은 지원 금지 사유가 아님). Day 10 이후 공고별 맞춤 지원을 매일 검토하고, 공고가 없으면 탐색·면접 훈련에 시간을 쓴다. 30일 이후에도 지원은 지속한다. 접수 공고가 드문 주에는 지원 건수를 억지로 채우지 않는다.

### 날짜별 기술 교육의 완료 판정

매일 최소한 (1) 설명 가능한 핵심 개념, (2) 정상 동작을 보여주는 **실행 결과**, (3) 실패 시 확인한 진단 자료, (4) 기록된 증거 경로, (5) 취업 작업 수행 여부의 **5개 항목을 체크**한다. 도구 설치가 됐다는 사실만으로 완료하지 않는다.

### Day 19 — 백업 계층 구분과 Linux 실제 파일 복구

- **학습 분야·키워드 / 목표 수준:** 백업 범위(파일·System State·VM), 복구 목표 RPO/RTO, 별도 백업 매체, 체크포인트와 백업의 차이, DC 복구 제약.
- **실습 (구체 행동·도구):** **필수 195분**: WEB01에 테스트 데이터와 Nginx 설정의 복사본 준비→해시 기록→원본과 별도 위치(가능하면 별도 VHDX/호스트 안전한 경로)에 백업→원본 삭제→복원→해시·HTTP 결과 확인. **선택**: 별도 저장 공간이 확인된 경우에만 비DC VM Export/Import를 수행하며 원본 VM 중복 IP 충돌 방지. DC01은 Windows Server Backup System State의 요구사항·절차를 정리하되 실제 백업은 충분한 매체·시간이 있을 때만 수행하고 **복원 성공이라고 주장하지 않음**.

- **실습 (구체 행동·도구):** **사전 조건:** Day 6에 WEB01→외부 IP로 NAT 경유 통신이 성공했을 때만 라우팅 장애를 실행. 정상 `ip route`, 내부 DC01 통신, 외부 IP 통신을 먼저 기록→WEB01 게스트의 **기본 게이트웨이만** 잘못된 10.77.10.254로 변경(사전 원복 명령 확보)→내부 10.77.10.10 통신은 정상, 외부 `ping 1.1.1.1` 또는 `curl --connect-timeout 5 https://1.1.1.1` 연결은 실패하는지 확인→경로 원복→재검증. **외부 IP가 ICMP 차단 시 NAT가 정상일 때 성공한 동일 외부 목적지·프로토콜로 비교.** NAT가 없다면 Packet Tracer의 두 서브넷/라우터로 경로 장애를 실습하고 이를 **시뮬레이션 증거**로 표시하며 HomeLab 장애 5건으로 계산하지 않음.

### 실행 승인 전 마지막 점검 (실측 없이는 조건부)

1. Day 1에서 `Get-Volume`, RAM/CPU, Hyper-V 상태, 기존 vSwitch/WinNAT, ISO 확보 상태를 측정한다.
2. Day 5~6에서 `LAB-INT` 격리와 WEB01의 실제 설치 패키지 확보를 증명한다.
3. Day 12 DHCP 시작 전에 **DC01 NIC가 Internal 스위치 하나에만 연결됨**을 호스트와 게스트에서 확인한다.
4. 실제 실행 시간과 오류는 계획을 실패로 숨기지 않고 다음 날 우선순위에 반영한다.
5. 30일 동안 정규직 취업 지원은 기술 완성 여부와 독립적으로 지속한다.

**현재 판정:** 계획의 논리적 모순은 상당 부분 해소했지만, 실행 성공과 채용 성과는 실측 전 검증할 수 없다. 이는 수정이 더 필요하다는 뜻과 구별한다. 문서상 큰 충돌이 없다면 사용자 승인 후 Day 1을 시작할 수 있는 **조건부 실행 후보안**이다.

### 우선순위 수정의 기록(설계 상 교차 점검)

- **이전 오류 예방 ①:** 학습을 30일 마친 뒤 포트폴리오·이력서를 시작하는 단계를 없앴다. Day 1 공고 분석·조건 부합 시 지원, Day 3 이력서, Day 6부터 구축 증거 누적.
- **이전 오류 예방 ②:** AD·DHCP를 물리 LAN에 유출시킬 수 있는 외부형 스위치 대신 Internal 스위치 우선 구성, NAT은 기존 충돌 확인 후 설치.
- **이전 오류 예방 ③:** Home Windows를 도메인 클라이언트로 잡지 않았다. 공식 Enterprise 평가 VM을 쓴다.
- **이전 오류 예방 ④:** '전원 끈 VM의 체크포인트'를 완전한 백업으로 주장하지 않고, 실삭제 후 복원 실증으로 평가한다.
- **이전 오류 예방 ⑤:** 모든 P1 주변기술을 P0와 같은 실습 숙련 대상으로 잡지 않았다. IPv6/Wi-Fi/VLAN/STP는 취업 전 기초를 포함하되 심화는 연기한다.
- **이전 오류 예방 ⑥:** 30일 180시간 안에서 완성 우선순위와 실패 시 축소 순서를 명시했다. **실습이 실제로 180시간 내 가능한지는 진행하면서 측정·재조정할 부분**이지 현재 보장할 수 있는 성질이 아니다.

### 이 설계가 '최선'이라고 단정할 수 없는 이유

이 계획은 **현재 알려진 제약과 확인된 채용공고 사례에 대해 실행 가능성을 높이도록 설계한 기준안**이지만, 실제 호스트 자원/OS 설치 소요시간, 서류 통과율, 채용담당자의 평가는 아직 측정되지 않았다. 따라서 '객관적으로 유일한 최적해'라고 단정하지 않는다. Day 1 실측과 Day 7/14/21/28 진행률·지원 반응을 기준으로 주간 재설계를 해야 현실적인 멘토링이 된다.

## 9. 실행할 때 멘토(이 채팅)의 운영 지침

- 하루 시작 시 `Day N`과 전일 결과만 전달받고 **설명 → 사용자 이해 확인 → 직접 명령 입력/실습 → 정상·실패 분석 → 최소 문서화 → 지원 작업** 순서로 안내한다. AI가 직접 실습했다고 주장하거나 사용자가 입력할 명령을 대신 실행했다고 기록하지 않는다.
- 사용자가 실제 출력·스크린샷을 보여주면 예상과 다를 때 **추측으로 성공 판정하지 않는다**. 오류 로그와 구성에 맞춰 수정한다.
- 멘토는 일별 완료 체크(개념/실습/복구/증거/취업)를 추적한다. 프로젝트 문서는 필요 최소한으로, 포트폴리오 공개 자료만 밀도 있게 작성한다.
- 포트폴리오 문장이나 이력서 문장은 사용자가 실습을 성공시켰음을 확인한 뒤 함께 작성한다.
- 한 주마다 `당초 계획 시간 / 실제 시간 / 밀린 작업 / 남은 현금흐름·지원 상황 / 다음 주 P0`를 점검하고 필요한 경우 계획을 축소한다. 현금흐름은 생활 결정을 직접 강요하는 항목이 아니라 구직기간 리스크 관리용이다.
